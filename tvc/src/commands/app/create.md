# tvc app create

## Purpose

Creates a TVC application by submitting a `createTvcApp` activity built from a JSON app
config file (normally generated by `tvc app init`). On success it records the new app ID
and manifest-set operator IDs in the local tvc config (`~/.config/turnkey/tvc.config.toml`)
as "last used" state for later commands (`deploy init`/`deploy create` defaults). Run it
once per app, after login (or with CI env auth) and after preparing an app config.

## Inputs

| input | flag | env | config key | default | prompted? |
|---|---|---|---|---|---|
| app config path | `-c`/`--config-file` | `TVC_APP_CONFIG` | — | none (required arg) | no |
| operator reuse opt-out | `--no-operator-reuse` | `TVC_NO_OPERATOR_REUSE` | — | false | no |
| debug-mode deployments | `--dangerous-enable-debug-mode-deployments` | `TVC_DANGEROUS_ENABLE_DEBUG_MODE_DEPLOYMENTS` | `dangerousEnableDebugModeDeployments` | false | no |
| app name | — | — | `name` | `<FILL_IN_APP_NAME>` | yes (placeholder fill) |
| quorum public key | — | — | `quorumPublicKey` | `KNOWN_QUORUM_KEY` (well-known insecure dev key) | never |
| enable egress | — | — | `enableEgress` | false | never |
| manifest set id | — | — | `manifestSetId` | null | never |
| manifest set params | — | — | `manifestSetParams` (name, threshold, newOperators, existingOperatorIds) | template: threshold 1, one operator with saved-or-placeholder key | name + operator keys, when placeholders |
| share set id | — | — | `shareSetId` | null | never |
| share set params | — | — | `shareSetParams` | null → hardcoded `dev-known-share-set` (threshold 2, 2 well-known keys) substituted at intent build (tvc/src/config/app.rs:213-223) | name + keys, only if placeholders present |
| auth | — | `TVC_ORG_ID`+`TVC_API_KEY_PUBLIC`+`TVC_API_KEY_PRIVATE` (all-or-none) | active org's stored API key | — | no |

Resolution-order notes:
- The debug-mode flag is deliberately one-way: flag/env can flip config `false → true`,
  but an absent flag never turns off a config `true` (tvc/src/commands/app/create.rs:345-351;
  documented in the global LONG_ABOUT, tvc/src/cli.rs:28-32).
- Everything except the three flags above is config-file-only — no flag/env layer exists
  for the domain fields, so for them the resolution order collapses to "config file or
  interactive fill".
- The `app init` template serializes every field create honors (AppConfig has no
  `skip_serializing_if`, so unset options appear as `null`) — template coverage is
  complete (tvc/src/config/app.rs:70-91, tvc/src/commands/app/init.rs:56-65).

## Interactive behavior

Interactive (default, TTY):
1. Reads `--config-file`. Any read failure (including file-not-found) silently falls back
   to a fresh placeholder template (tvc/src/commands/app/create.rs:182-185).
2. Validates; placeholder errors trigger `fill_interactively` prompts in order: App name →
   Manifest set name → per-operator `Operator '<name>' public key` (default: the active
   org's default-backend operator key, best effort) → Share set name → share operator keys.
   Only `<FILL_IN`-prefixed fields are prompted; quorum key, egress, thresholds,
   manifestSetId/shareSetId, and debug mode are never prompted (tvc/src/config/app.rs:114-141).
   Non-placeholder validation errors (conflicting/missing set fields, low share threshold) bail.
3. If anything was filled: `Save filled config to <path>?` (default yes) writes the file back.
4. Operator-reuse decision (after fill, before the API call): if exactly one new manifest
   operator is requested, no `existingOperatorIds` are set, and known candidates' proven
   keys match it — a sole match is reused automatically (announced on stdout); multiple
   matches prompt `Select operator to reuse`. That prompt additionally requires a TTY even
   in "interactive" mode; piped stdin bails with remediation (tvc/src/commands/app/create.rs:80-95).

Non-interactive (`--non-interactive` / `TVC_NON_INTERACTIVE` / `--message-format json`):
the config file must exist, parse, and validate with zero placeholders (hard requirement);
multiple reuse candidates bail with the same remediation message (set
`manifestSetParams.existingOperatorIds` or pass `--no-operator-reuse`). A sole matching
candidate is still auto-reused, silently in JSON mode.

## Outputs

Human: `Creating app '<name>'...` progress line; optional `Reusing operator <op> (pass
--no-operator-reuse to create a new one)`; optional `Wrote <path>`; then the terminal
block: App ID, Name, Manifest Set ID, Manifest Set Operator IDs (when non-empty), Config
path, and a hint to use `tvc deploy approve --operator-id`
(tvc/src/commands/app/create.rs:295-325).

JSON: one terminal message, reason `app_created`, fields `appId`, `name`, `manifestSetId`,
`manifestSetOperatorIds`, `configPath` (tvc/src/outcome.rs:53). All `shell_println!`
progress (including the reuse announcement) is suppressed in JSON mode
(tvc/src/output.rs:242-254). Errors: reason `command_error` with a `code` (see below).

## Side effects

- Reads the app config JSON; may rewrite it (interactive save-back, pretty-printed).
- Reads `~/.config/turnkey/tvc.config.toml` (dispatch creates a default one if absent,
  tvc/src/cli.rs:219-223); after creation writes `last_created_app_id` and
  `last_operator_ids` for the active org back to it (tvc/src/commands/app/create.rs:272-274).
- Best-effort reads of the default operator's key material for the prompt default: local
  key file, or the YubiKey registry's cached key — no device I/O (tvc/src/operator.rs:282-304).
- Turnkey API: one `create_tvc_app` activity (env-var or stored API-key auth,
  tvc/src/client.rs:48-64). No YubiKey device interaction.

## Failure modes

- Missing `--config-file` arg: clap usage error, exit 2 (`usage_error` in JSON).
- Unreadable/unparseable config (non-interactive), invalid config (both modes),
  multiple-candidate bail, "no active organization set": plain anyhow → code
  `command_error`, exit 1. This command never produces `MissingRequiredInput`, and
  `ErrorCode::InvalidInput` is dead code repo-wide (tvc/src/errors.rs:54-56).
- API failures classify via the typed `TurnkeyClientError` chain: `unauthorized`,
  `not_found`, `api_error`, `network_error`, `client_version_too_old` (tvc/src/errors.rs:93-103).
- Post-creation local-config bookkeeping failure (`set_last_app_id` / `save`): exit 1
  even though the app was created (see Gap 1).

## Gaps

1. **[bug?] Under pure env-var (CI) auth the command creates the app, then reports failure and never emits the app ID.**
   `build_client` explicitly supports auth with only `TVC_ORG_ID`/`TVC_API_KEY_PUBLIC`/`TVC_API_KEY_PRIVATE`
   and no `tvc login` (tvc/src/client.rs:48-64; promised in tvc/src/cli.rs:34-38), but after the
   successful `create_tvc_app` call, `config.set_last_app_id(&app_id)?` bails with
   "no active organization set" when `active_org` is `None` (tvc/src/commands/app/create.rs:272,
   tvc/src/config/turnkey/mod.rs:699-707) — the fresh default config written by dispatch has no
   active org (tvc/src/cli.rs:219-223). Exit 1, no `app_created` outcome, app ID lost to the
   caller. Any post-create `config.save()` failure masks success the same way. `tests/auth_env.rs`
   only covers the read-only `app status` under env auth.

2. **[capability] Operator reuse can only ever match hosted operators; registered local and YubiKey identities are never candidates.**
   `known_operator_candidates` surfaces hosted registry records (with proven keys) plus
   last-app-create bare IDs that deliberately carry `public_key: None`
   (tvc/src/operator.rs:448-475, 219-222), and `decide_operator_reuse` only matches candidates
   with a proven key (tvc/src/commands/app/create.rs:143-147) — so bare IDs are inert and reuse
   fires exclusively for hosted operators. A `LocalOperatorRecord` can carry both an
   `operator_id` and a loadable key file (tvc/src/config/turnkey/mod.rs:338-347), and the YubiKey
   registry caches its key (tvc/src/operator.rs:298-302), yet neither is offered: the common
   local-operator flow re-running `app create` with the same key silently mints a duplicate
   server-side operator unless the user hand-edits `existingOperatorIds`. Acknowledged as a
   known limitation in tests/app_create.rs:221-223. This is the brief's canonical shape:
   registry state constrains which operator identity the user's explicit key can resolve to.

3. **[capability] No way to choose a secure quorum key through init or the interactive fill — the well-known insecure dev key is applied silently.**
   The template hard-codes `KNOWN_QUORUM_KEY` ("for applications that do not need secure quorum
   keys", tvc/src/config/app.rs:65-66, 73) and `fill_interactively` never prompts for
   `quorumPublicKey` (tvc/src/config/app.rs:114-141), so both `app init --interactive` and
   `app create`'s fill walk produce an app on the shared dev quorum key without ever surfacing
   the choice; the outputs of `keys create-quorum-key` / `keys generate-local-quorum-key` can
   only be wired in by hand-editing JSON. Same silent-default pattern for the hardcoded
   `dev-known-share-set` substituted when `shareSetParams` is null (tvc/src/config/app.rs:213-223)
   — nothing in human output says the well-known share keys were used.

4. **[consistency] Only debug mode gets a flag/env override; `deploy create` overrides every config field and makes the file optional.**
   `deploy create` pairs each config field with flag+env (`--app-id`/`TVC_APP_ID`,
   `--qos-version`, ports, replicas, pivot args…, tvc/src/commands/deploy/create.rs:88-152)
   and supports flag-only creation with `--config-file` omitted (deploy/create.rs:74-75).
   `app create` requires the file and offers no `--name`, `--quorum-public-key`,
   `--enable-egress`, `--manifest-set-id`, `--share-set-id`, or threshold overrides
   (tvc/src/commands/app/create.rs:30-56), so CI pipelines must template JSON to vary
   anything but debug mode. Minor adjunct: `app init` defaults output to `app.json`
   (tvc/src/commands/app/init.rs:19-26) but `app create --config-file` has no default, so
   the advertised init→create pairing still requires retyping the path.

5. **[bug?] Interactive mode swallows every config-file read error, not just file-not-found.**
   `Err(_) => AppConfig::template(None)` (tvc/src/commands/app/create.rs:182-185) treats
   permission-denied, is-a-directory, or any I/O failure on an existing file as "start a fresh
   template walk", then offers to save over the same path — a typo'd or unreadable
   `--config-file` silently becomes a from-scratch app instead of an error. `deploy create`
   propagates read errors and only falls back when no path was given
   (tvc/src/commands/deploy/create.rs:251-261).

6. **[docs] The documented `invalid_input` error code is unreachable, and this command's validation failures — its poster child — emit `command_error`.**
   The global LONG_ABOUT defines `invalid_input` as "semantic validation failed in the command"
   (tvc/src/cli.rs:56), but `ErrorCode::InvalidInput` is `#[allow(dead_code)]`
   (tvc/src/errors.rs:54-56) and `invalid_app_config_error` is a bare `anyhow!`
   (tvc/src/commands/app/create.rs:231-233), so config-validation failures classify as the
   `command_error` fallback. Likewise the non-interactive multiple-candidates bail
   (create.rs:86-91) is a missing-input shape that classifies as `command_error` rather than
   `missing_required_input`. JSON consumers cannot distinguish these from generic failures.
